## 4. Рендерер без NMS (`renderer: display`) — единственный способ иметь голограммы на 1.21+/26.x

См. `../BUILD-HERE.md`. Кратко по существу оптимизации:

- Пакет-рендерер HD умеет говорить с сервером только версий 1.8.4–1.20.4 (имя NMS-пакета + сырые ID пакетов
  и DataWatcher). На 1.20.5+ он **не стартует**, и «подставить старый адаптер» нельзя: байты пакетов не совпадут,
  и вместо проблемы с FPS получится обрыв соединений у Geyser-игроков.
- Display-рендерер не пишет пакеты сам: он создаёт обычные сущности (`ARMOR_STAND`-маркер с ни́метегом,
  `ITEM`, `INTERACTION`) и управляет тем, кому они показаны, через `Player#showEntity/hideEntity`.
  Это версионно-независимо, поэтому работает и на 26.2.
- Побочный эффект для производительности: скрытая для игрока голограмма перестаёт существовать для него на уровне
  сети (не «спавн, потом destroy», а ничего), а сущности существуют только пока у строки есть зрители.
- Пакеты отправляются тем же `PacketSenderExecutor`, что и раньше, но сами Bukkit-вызовы перенесены в главный тред
  (задача-флеш раз в тик): создавать/двигать сущности вне главного треда нельзя.
- Опциональные методы (`setMarker`, `setSmall`, `setSilent`, `setInvulnerable`, `setPersistent`,
  `setVisibleByDefault`, `addPotionEffect`, persistent-данные) вызываются рефлексией через `DisplayReflect`:
  модуль `core` компилируется против API 1.8, а отсутствующий метод должен означать «эта версия так не умеет»,
  а не падение плагина.

## Профиль spark: что урезано дополнительно (сборка от 2026-10-27)

По снимку `HolographicDisplays (v3.0.5-optimized-bedrock)` на живом сервере (0,38% потока сервера) узкие места
оказались не в отрисовке, а в служебных циклах тика. Что изменено:

| было в профиле | правка |
|---|---|
| `LineClickListener.processQueuedClickEvents()` 0,04% — итератор + `clear()` пустого множества каждый тик | флаг `hasQueuedEvents`: при отсутствии кликов метод ничего не делает |
| `ActivePlaceholderTracker.clearInactivePlaceholders()` → `TickExpiringMap.clearUnusedEntries()` 0,09% — `removeIf(lambda)` каждый тик | явный `Iterator` вместо `removeIf` (без создания лямбды/захвата на каждый вызов) + запуск раз в 5 тиков (окно истечения записей — 10 тиков, так что потерь нет) |
| `LineTrackerManager.update()` + обход всех игроков, когда голограмм нет | `isEmpty()`-быстрый путь: если строк нет, тик ограничивается обновлением координат, без списков и проверок радиуса |
| `BedrockGuard.tick()` 0,04% | координаты игрока читаются один раз на тик (`needsScan` → `scan`, а не дважды); список зарегистрированных голограмм строится один раз на тик и переиспользуется всеми сканируемыми игроками; пустые очереди показа/скрытия не заходят в обработку |
| `CachedPlayer.onTick()` 0,10% (`CraftEntity.getLocation()` → `getWorld()`) | оставлено как есть: это единственный способ узнать, двигался ли игрок, не перебирая все голограммы; аллокаций больше одной на игрока в тик там нет |

Что это значит практически: фиксированная стоимость тика HD перестала расти с числом плейсхолдеров и кликов, а
на сервере без голограмм тик почти ничего не стоит. При 3 онлайн это ~тысячные процента — **HolographicDisplays не был источником ваших просадок FPS** — это видно и по самому снимку: 0,38% потока сервера на весь плагин.

## 5. Клиентский FPS (рендерер `display`) — что изменено

Серверный тик к просадкам FPS на телефоне отношения не имеет: FPS режет **число сущностей с именигами, которые
клиент рисует каждый кадр**, и то, как часто эти сущности пересоздаются. Изменено в рендерере:

1. **Пересоздание сущности при смене текста убрано.** Если игроку уже показана нужная сущность, `showEntity` больше
   не отправляется — раньше каждое обновление текста (плейсхолдер) заново слало спавн-пакет, клиент ронял и
   пересобирал объект отрисовки с нулевой пользой. Теперь обновление текста = одно изменение имени.
2. **`display.text-update-interval-ticks` (по умолчанию 3)** — имя сущности переписывается не чаще, чем раз в N
   тиков. Быстро меняющиеся плейсхолдеры (здоровье, TPS, координаты, `refresh-interval-ticks: 1` у голограммы)
   больше не заставляют клиент перерисовывать нижейт 20 раз в секунду. Новые зрители и первичное показание
   не задерживаются: троттлинг касается только уже видимой строки. `1` — обновлять каждый тик, как было.
3. **Разнос синхронизации при входе** — после join/respawn/sмены мира видимость всех строк применяется не одним
   пакетным залпом, а по 24 строки за тик. Ровно этот залп и бывает причиной «при заходе крашит» на мобильных
   клиентах и на соединениях с небольшим буфером.
4. **`display.interaction-entities: false`** — у кликабельных строк отключается невидимая сущность-хитбокс
   (`INTERACTION`): минус одна сущность на строку и минус один тип сущностей, который не все клиенты умеют.
5. Позиция строки применяется **до** троттлинга, поэтому идущая за игроком голограмма не отстаёт из-за частой смены
   текста.

### Настройки, которые дают основной прирост FPS
Сколько именигов игрок видит одновременно — это `bedrock-guard`, а не версия рендерера. Для Purpurbedrock без
Floodgate автоопределение телефона не срабатывает, поэтому включать надо явно:

```yaml
settings:
  view-range: 32          # было 48: меньше сущностей попадает в вид
bedrock-guard:
  enabled: true
  detection: everyone     # на сервере без Floodgate/Geyser-API иначе не действует ни на кого
  view-range: 16
  max-visible-lines: 8    # максимум строк с именигами на игрока
  max-lines-per-tick: 4   # темп показа при входе, чтобы не затапливать соединение
```

или командами, без рестарта: `/holograms bedrockguard everyone`, `radius 16`, `budget 8`, `status`.

### Если краш при входе останется
Проверить по очереди (каждый пункт — отдельная проверка, рестарт не нужен для 1-3):
1. `display.interaction-entities: false` + `/holograms reload` — если отпустило, клиент ругается на `INTERACTION`;
2. `bedrock-guard.enabled: false` — снимает все показ/скрытия per-player;
3. временно `renderer: packets` не поможет: он поддерживается только до 1.20.4.
Нужен `crash-reports/latest.txt` клиента и строки из консоли сервера — по ним видно, чей пакет.

## 6. Клиентские мелочи, которые видны глазами

## Приветственная голограмма встроена в плагин

`Default hologram. Change it with /holo edit` — это не «арморстенд плагина», а голограмма, созданная командой
`/holo create` без текста: она лежит в `plugins/HolographicDisplays/database.yml` и удаляется командой
`/holo delete <имя>` (`/holograms list` покажет имя).

Сборка `2026-10-28` умеет саму голограмму спавна: **если база голограмм пуста**, при старте создаётся голограмма
`welcome` со строками `icon: BEACON`, заголовком VoidPe, приветствием и ссылкой на телеграм-канал — на координатах
из вашего конфига DecentHolograms (`world -6.5 68.5 0.5`). Она сохраняется в `database.yml` как обычная:
правится `/holo edit welcome`, двигается `/holo moveHere welcome`, удаляется `/holo delete welcome` — и обратно уже
не возвращается, потому что база перестаёт быть пустой.

Ключи (все необязательные, значения по умолчанию = ваш конфиг):

```yaml
welcome-hologram:
  enabled: true
  world: world
  x: -6.5
  y: 68.5
  z: 0.5
```

Гекс-цвета `&#1E90FF` HD не поддерживает (плагин таргетит кодировку 1.8), палитра переведена в ближайшие
legacy-коды; индивидуальные `height` у строк в HD тоже нет — интервал общий `space-between-lines`.
Ручной вариант вместо «пустой базы»: файл `voidpe-welcome-database.yml` в корне репозитория — это готовый
`database.yml`, его можно положить в `plugins/HolographicDisplays/` и сделать `/holograms reload`.

## 7. Исправление: спам `UnsupportedOperationException` в консоли

Симптом: `Task #41 for HolographicDisplays ... generated an exception
java.lang.UnsupportedOperationException at CopyOnWriteArrayList$COWIterator.remove ... DisplayNMSManager.flush`.

Причина: `lines` рендерера — `CopyOnWriteArrayList` (он нужен для потокобезопасного `addIfAbsent` из потока отправки
пакетов), а освобождённую строку я удалял через `Iterator#remove`, который у COW-итератора всегда бросает это
исключение. Дальше то же самое пытался сделать `catch`-блок, исключение уходило в Bukkit, и Bukkit повторял таск
каждый тик: консоль заливалась, а освобождённые строки **никогда не выписывались** из рендерера (то есть их `tick()`
продолжал вызываться вечно — маленькая утечка и лишняя работа на тик).

Исправлено: во время прохода ничего не удаляется, завершённые строки собираются в список и снимаются одним
`lines.removeAll(finished)`. Плюс `unregister()` проверяет `hasPendingRequests()`: если запрос на показ пришёл, пока
строка освобождалась, она регистрируется обратно, чтобы голограмма не осталась невидимой. Заодно в `ci/build.sh`
добавлен `actions/cache` на `~/.m2/repository` и жёсткие сетевые таймауты — сборки на Actions перестали виснуть на
загрузке зависимостей (было: 22+ минуты и `maven exit code: 124`).
